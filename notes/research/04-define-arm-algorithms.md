## How to interpret the define's derivation metadata (structural notes)

- All `MethodDef` are `Type="Computation"`; none carry a populated `FormalExpression` (no `Context`/code) — algorithms are **prose only**, in `MethodDef/Description/TranslatedText`.
- Derivations exist at two granularities: **variable-level** (referenced by `ItemRef/@MethodOID`, OID like `MT.ADAE.ASTDT`) and **value/parameter-level** (OID like `MT.ADLBC.AVAL.ALB`, i.e. `MT.<DS>.<VAR>.<PARAMCD>`). ADAE, ADLBC, ADLBH, ADSL have rich variable-level text; ADADAS, ADCIBC, ADNPIX, ADVS have **empty variable-level methods** and carry their logic only at the value level (matching the ReadMe's "missing information" caveat, which named ADADAS specifically).
- There are **1,533 `def:WhereClauseDef`** (each a single `RangeCheck` with `def:ItemOID` + `Comparator="EQ"` + one `CheckValue`, e.g. `WC.ADADAS.DTYPE.EQ.ACITM01` → `IT.ADADAS.DTYPE EQ ACITM01`). These encode the per-PARAMCD value partitions, **but there are ZERO `def:ValueListDef` elements** — so the where-clauses and value-level methods are not formally wired to a value list. This is a known artifact of the Pinnacle 21 generation and means value-level metadata cannot be resolved through the normal `ItemDef → def:ValueListRef → ValueListDef → ItemRef(WhereClauseRef, MethodOID)` chain. I resolved them by OID-name convention instead.
